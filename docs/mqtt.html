MQTT contract

Three topics, one direction

The node publishes and never subscribes. There is no command topic, no remote configuration and no code path that acts on an incoming message. Everything the node will ever say fits in three topics, and this page is the contract for all of them.

Broker1883
QoS0
Keepalive30 s
Publish rate0.5 Hz
Buffer512 B

Topic tree

Node identity

The node id is the last three bytes of the Wi-Fi station MAC, read straight from eFuse with esp_read_mac(). It is also used verbatim as the MQTT client id. 

uint8_t mac[6];
esp_read_mac(mac, ESP_MAC_WIFI_STA);
snprintf(id, sizeof(id), "%02x%02x%02x", mac[3], mac[4], mac[5]);

Why not WiFi.macAddress()

Because it returns all zeros until the Wi-Fi driver has actually started. Reading it during mqttInit() gave every node the id 000000, and a shared client id makes a broker disconnect each node as the next one connects. The symptom was nodes that worked perfectly alone and knocked each other offline in pairs. Reading eFuse directly does not depend on driver state and cannot fail this way.

Telemetry payload

One JSON object every two seconds, not retained. Retaining it would mean a late subscriber gets a stale reading presented as current, which is worse than getting nothing. 

{
  "ts": 1789412204,
  "ts_valid": true,
  "uptime_ms": 41284,
  "seq": 20,
  "temp_c": 23.71,
  "hum_pct": 58.20,
  "lux": 412.5,
  "sound_avg_db": 44.3,
  "sound_peak_db": 51.8,
  "sound_calibrated": true,
  "alerts": "---",
  "rssi": -58
}
FieldTypeUnitMeaning
tsintegersUnix seconds, UTC. Zero when the clock has not synced.
ts_validbooleanFalse means ignore ts and use arrival time instead.
uptime_msintegermsMilliseconds since boot. Usable as a monotonic axis when ts is not.
seqintegerIncrements per publish, resets on reboot. A gap means lost messages, a reset means the node restarted.
temp_cfloat | null°CTwo decimals. Null when the SHT3x read failed.
hum_pctfloat | null%Two decimals. Null and non-null together with temp_c.
luxfloat | nulllxOne decimal. Null when the BH1750 read failed.
sound_avg_dbfloatdBMean across the ten sub-windows. Relative, not dB(A).
sound_peak_dbfloatdBLoudest sub-window. This is what the alarm tests.
sound_calibratedbooleanFalse means MIC_CAL_DB is unset and both dB figures are tens of dB high.
alertsstringExactly three characters, positional: temperature, light, sound. Each is its letter or a dash.
rssiintegerdBmWi-Fi signal strength at publish time.

Failed readings are null, never zero and never NaN

JSON has no NaN literal, and zero is a plausible temperature. A helper writes the literal null whenever a sensor read failed, so a consumer can tell "the room is at 0 °C" from "we do not know". Check for null before arithmetic; the Node-RED validate function does exactly this.

Status and last will

A retained topic carrying one of two literal strings. This is how a dashboard distinguishes a quiet room from a dead node, which is a distinction the telemetry stream cannot make on its own: both look like an absence of messages.

PayloadPublished byWhen
onlineThe nodeImmediately after a successful connect.
offlineThe brokerAutomatically, once the keepalive lapses without contact.

The second row is the important one. offline is registered as the connection's Last Will at connect time, so the broker publishes it on the node's behalf when the node is no longer in a position to publish anything. A node that loses power, loses Wi-Fi or crashes still reports its own absence. 

mqtt.connect(nodeId, user, pass,
             topicStatus, /* willQos */ 0, /* willRetain */ true, "offline");

Retained means a subscriber connecting later still receives the current state immediately rather than waiting for the next change, which for a healthy node might never come.

Alert state

Retained JSON, published only when the combined alert state changes rather than on every sample. 

{"temp": false, "light": true, "sound": false}

Internally the three flags are packed into a bitmask and compared against the last one published; identical masks publish nothing. The mask is reset on every reconnect, which forces a fresh publish so the retained value cannot be left describing a state from before a network drop.

This duplicates information already in the telemetry alerts string, and that is intended. A subscriber that only cares about alarms can subscribe to one low-traffic retained topic instead of parsing a message every two seconds.

Time handling

Telemetry timestamps are UTC. The panel clock is not. These are two different settings and confusing them silently re-timestamps every message the node has ever sent.

ConstantValueAffects
GMT_OFFSET_SEC0The system clock, and therefore every ts in the telemetry stream. Leave at zero so stored data is unambiguous across sites.
DST_OFFSET_SEC0Also the system clock. Also leave alone.
DISPLAY_TZ_OFFSET_SEC8 × 3600The panel clock only. This is the one to change for a local time display.

Validity is decided by a single test: any clock reading past 1700000000, which is late 2023, is treated as synced. An ESP32 with no NTP answer starts counting from 1970, so the comparison separates a real time from an uninitialised one without needing to track whether NTP replied.

Subscribing

Node-RED takes all telemetry from all rooms and all nodes with one wildcard subscription, then splits the topic to recover the room and node ids as message properties. 

classroom/+/+/telemetry     // every node, every room
classroom/room-101/+/#      // one room, all three topics
classroom/+/+/status        // liveness across the whole estate
const parts = msg.topic.split('/');
msg.room = parts[1];
msg.node = parts[2];

Because room and node live in the topic and not the payload, they cost nothing to publish and cannot drift out of sync with where a message actually came from.

Broker config

Mosquitto 2, configured in eleven lines. Persistence is on so queued state survives a restart, and logging goes to stdout so docker compose logs shows activity. 

listener 1883
allow_anonymous true

persistence true
persistence_location /mosquitto/data/

log_dest stdout
log_type notice

allow_anonymous true is a bench setting

Any device on the LAN can currently publish to any topic in this tree, including plausible-looking fake telemetry, and can read everything the nodes send. That is acceptable on an isolated bench network and nowhere else. Before this runs in a real building it needs a password file, per-node credentials, and topic ACLs restricting each node to its own subtree.
