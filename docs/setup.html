Build & bring-up

From an empty board to a live dashboard

Budget two to three hours the first time, most of it waiting on downloads. The order here is not arbitrary. Each stage ends with something you can check, and a check that fails tells you which stage broke rather than leaving you with a dead board and five suspects.

Prerequisites

Three things to have before starting.

  • Your PC's LAN address. Run ipconfig on Windows or ip addr on Linux and note the IPv4 address on your local network. The node needs this to find the broker, and localhost will not do: the node is a separate machine.
  • The ESP32 wired. All sensors and, if you are using it, the display. See pins and wiring.
  • A phone SPL meter app. Needed for the microphone calibration, which cannot be skipped if you want the sound alarm to work.

Toolchain

  1. Install the Arduino IDE and the ESP32 board package

    Then set the board and its options exactly as below. The PSRAM setting in particular is not the default.

    All from the Library Manager. The first pulls in a dependency you should accept.

    Needed for the backend, not for the node. If Docker Desktop will not run on your machine, the four services can be installed natively instead, at the cost of doing four installs and four config files by hand.

Credentials

Wi-Fi and broker credentials live in secrets.h, which is gitignored and not in the repository. Create it from the template. 

cd CR_Monitor
cp secrets.example.h secrets.h

Then fill in the real values.

const char* WIFI_SSID     = "YOUR_WIFI_SSID";
const char* WIFI_PASSWORD = "YOUR_WIFI_PASSWORD";

// Leave both empty for an anonymous broker.
const char* MQTT_USER = "";
const char* MQTT_PASS = "";

Two more values live in CR_Monitor.ino itself and need editing per install: 

const char* MQTT_HOST = "192.168.1.5";   // your PC's LAN IP
const char* ROOM_ID   = "room-101";      // this node's room

Which file is the real sketch

CR_Monitor/CR_Monitor.ino. A copy exists at the repository root as CR_Monitor.cpp; it is a working duplicate, it is gitignored, and it is behind. Older notes in SETUP_GUIDE.txt describe the opposite arrangement and are stale. Open the .ino.

TFT_eSPI pin map

This is the step that most often gets skipped

TFT_eSPI does not read its configuration from your sketch folder. It reads it from inside its own installed library directory. The pin map is versioned in this repository so it is not lost, but a copy in the repo has no effect on a build: you have to install it. Miss this and the display will not work no matter how correct your wiring is.

Pick either approach.

  • Copy the body of CR_Monitor/TFT_Setup_CR_Monitor.h over TFT_eSPI/User_Setup.h in your Arduino libraries folder, or
  • place the file in the TFT_eSPI folder and point User_Setup_Select.h at it.

The file selects the driver as well as the pins. Exactly one driver may be active, and it is set to ILI9481_DRIVER, confirmed against this panel on 2026-09-13.

If the screen is white but the backlight is lit

A wrong driver produces exactly this: the init sequence means nothing to the controller, so nothing is ever drawn. It is also what a missing 3.3 V logic supply looks like, so rule out the regulator question first. Then work down the commented driver list in the setup header, reflashing each time. This panel was assumed to be HX8357D for a while, which is why it stayed white; the pin map had been right the whole time.

Bring-up order

Five single-purpose sketches, each proving one thing. Run them in this order on a board you have not run before. Each takes under a minute and saves considerably more than that.

SketchProvesPass looks like
Test_RailSupply rails are where they should be.Measured millivolts within tolerance.
I2C_ScanThe bus works and devices acknowledge.0x44 and 0x23 found
Test_SHT3xTemperature and humidity read plausibly.Room temperature, stable.
Test_BH1750Illuminance responds to light.Value drops when you cover the sensor.
Test_TFTThe parallel bus and pin map are correct.A solid red screen.

If I2C_Scan finds nothing, check SDA on GPIO8, SCL on GPIO9, that 3.3 V is actually present at the sensors, and that they share a ground with the ESP32. That combination accounts for nearly every empty scan.

Flash the node

  1. Open and upload CR_Monitor.ino

    Then open Serial Monitor at 115200 baud.

  2. Read the self-test

    The boot report runs before anything else and tells you what the node thinks of its own hardware. Two beeps at the end are the buzzer self-test. Do not move on with a FAIL on the bus or the microphone.

  3. Confirm the panel and the CSV

    A boxed status block and a CSV row should appear every two seconds, and the TFT should show four cards with live values. 

    +------------------------------+
| Classroom Monitor
| Temp : 23.7 C
| Humid: 58.2 %
| Light: 412 lx
| Sound: 52 dB peak (avg 44 dB, 1.31 mVrms)
| Wi-Fi: connected
| MQTT : connected, seq 20, time ok
+------------------------------+

Calibrate the microphone

Do this before trusting any decibel figure, and before the sound alarm will arm at all. The node ships with sound_calibrated reporting whether this has been done.

First check the raw statistics printed by SOUND_DEBUG. In a quiet room the mean should be around 1900 to 2100 counts with a peak-to-peak of a few tens. A drifting mean with large random swings means a floating pin, not a loud room.

Then follow the four-step procedure on the firmware page: zero the constant, read the panel, measure the room with a real meter, and set the constant to the difference. Verify at the loud end afterwards, because an error that only appears when loud is the amplifier clipping and needs the trimpot turned down instead.

Inside the stack, use container names and not localhost

Node-RED talks to InfluxDB at http://influxdb:8086 and to the broker at host mosquitto. From inside a container, localhost means that container itself, so a connection to localhost:8086 goes nowhere. Use localhost only in your own browser.

Verify the stream

Before building anything downstream, confirm messages are actually arriving. Install MQTTX, connect it to your PC's LAN IP on port 1883, and subscribe to: 

classroom/#

You should see a telemetry object every two seconds, plus a retained status of online that arrives the moment you subscribe. If telemetry is flowing but nothing reaches Node-RED later, the problem is downstream of here, which is worth knowing now.

InfluxDB

  1. Complete initial setup

    Open http://localhost:8086 and work through the first-run wizard. Set the organisation to classroom and the initial bucket to sensors. These names are referenced by both Node-RED and Grafana.

  2. Create an API token

    Generate a token with write access to the sensors bucket. Copy it somewhere outside the repository; you will paste it into Node-RED and Grafana, and it is shown in full only once.

Do not paste the token into a tracked file

Not into a sketch, not into a notes file, not into a setup guide. Anything committed to git stays in the history even after you delete it, and a repository that is private today may not be tomorrow. Keep tokens in the tools that need them. If one does end up committed, revoking and reissuing it in InfluxDB is the fix; deleting the line is not.

Node-RED

Three nodes in a line, plus an optional debug tap. This is where raw MQTT becomes rows in a database, and where impossible readings get rejected.

  1. Install the InfluxDB nodes

    Menu, then Manage palette, Install tab, search node-red-contrib-influxdb, install.

  2. Add an mqtt in node

    Servermosquitto
    Port1883
    Topicclassroom/+/+/telemetry
    Outputa parsed JSON object
    QoS0

  3. Add a function node named validate

    It does two jobs: drop anything not shaped like this project's telemetry, and reject physically impossible values so one bad reading does not end up in a chart forever. 

    const d = msg.payload;
// drop anything not shaped like our telemetry
if (typeof d !== 'object' || d.seq === undefined) return null;

// range sanity - reject impossible readings
const bad =
  (d.temp_c  !== null && (d.temp_c  < -10 || d.temp_c  > 60)) ||
  (d.hum_pct !== null && (d.hum_pct < 0   || d.hum_pct > 100)) ||
  (d.lux     !== null && (d.lux     < 0   || d.lux     > 120000)) ||
  (d.sound_peak_db < 0 || d.sound_peak_db > 140);
if (bad) { node.warn('rejected: ' + JSON.stringify(d)); return null; }

// split topic classroom/<room>/<node>/telemetry
const parts = msg.topic.split('/');
msg.room = parts[1];
msg.node = parts[2];
return msg;

    Note that each numeric check is guarded against null first. A failed sensor read publishes null, and comparing null against a number would silently reject a perfectly good message.

  4. Add an influxdb out node

    Version2.0
    URLhttp://influxdb:8086
    Tokenthe token from the previous section
    Organizationclassroom
    Bucketsensors
    Measurementreading

  5. Deploy and watch

    Wire a debug node off the validate output. After deploying, a validated object should appear in the Debug panel every two seconds, the mqtt node should read connected, and the InfluxDB node should show no error.

Confirm the data landed before moving on. In the InfluxDB Data Explorer, query bucket sensors, filter _measurement = reading and _field = temp_c, and you should see a live line.

Grafana

  1. Add InfluxDB as a data source

    Open http://localhost:3000, sign in with admin / admin, set a new password, then Connections, Data sources, Add data source, InfluxDB.

    Query languageFlux
    URLhttp://influxdb:8086
    Organizationclassroom
    Tokenthe same token
    Default bucketsensors

    Save and test should report that the datasource is working.

  2. Build the first panel

    New dashboard, add visualization, pick the InfluxDB source, and paste this Flux query.

    from(bucket: "sensors")
  |> range(start: -6h)
  |> filter(fn: (r) => r._measurement == "reading")
  |> filter(fn: (r) => r._field == "temp_c")

  3. Repeat for the other three series

    Change the final filter to hum_pct, lux and sound_peak_db in turn. Arrange the panels and save the dashboard.

At this point the pipeline is complete

Sensors to broker to validation to storage to dashboard, updating every two seconds. What remains is what turns a working demo into an actual study: the occupancy stream, the comfort responses, and the analysis that puts the two against the sensor data.

Before real use

The defaults here are chosen for getting a bench build working, and several of them are wrong for a building with people in it. None is hard to fix; they just have to be done deliberately.

DefaultRiskFix
allow_anonymous true Anyone on the LAN can read all telemetry or inject convincing fake readings. A Mosquitto password file, per-node credentials, and topic ACLs limiting each node to its own subtree.
admin / admin Grafana ships with a known password. Change it at first login, which Grafana prompts for. Do not skip the prompt.
port 1883 Credentials and payloads cross the network in plain text. TLS on 8883 once authentication is in place.
all-access API token A single token with full organisation rights in two config fields. Separate tokens: write-only to sensors for Node-RED, read-only for Grafana.
thresholds in firmware Placeholder limits presented as if they were standards. Cite a source for each band before publishing any findings from the data.

One thing that is already right and worth keeping right: the sound path never records audio, and the planned occupancy input is a bucket rather than a headcount. Those are the properties that make the monitor something a room full of people can reasonably be asked to accept, and they are easy to erode by accident once someone wants better data.
