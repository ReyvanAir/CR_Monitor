Firmware

What the node does between one reading and the next

641 lines of Arduino C++ across four files. No RTOS tasks, no interrupts, no delay() in the running loop. Everything is cooperative: each service gets a turn, does the smallest amount of work it can, and returns. That constraint is what keeps a two second sample period honest while Wi-Fi is reconnecting.

The two headers are included from the middle of the sketch, not the top

TFT_Panel.h sits after the global declarations because it reads them directly: soundMaxDb, seq, the mqtt client, the three alert flags. Preflight.h comes after TFT_Panel.h so its display check can call into the panel and read it back. Moving either to the top of the file will not compile, and the ordering is the reason.

Boot sequence

setup() runs in a fixed order, and the order matters more than it looks. Hardware is proved before it is trusted, and the microphone is characterised before Wi-Fi is allowed to start adding noise to the ADC.

  1. Serial first, then flush

    115200 baud, then a banner and an explicit Serial.flush(). If that banner never appears, the hang is somewhere before setup() and nothing below is worth debugging yet.

  2. Buzzer silent, ADC configured

    12 bit resolution, and 11 dB attenuation on three pins: the microphone, plus TFT_DC and TFT_CS, because those double as touch electrodes and get read as analogue inputs on the same range.

  3. Bus self-test

    preflightBus() checks the I²C lines and enumerates devices. It brings Wire up as a side effect, which is why the sensor begin() calls further down do not start it themselves.

  4. Display up, then checked

    tftBegin(), then preflightDisplay() reads the panel back to confirm the bus actually works, then preflightSummary() on serial and tftPreflight() puts the same report on the screen before handing over to the dashboard.

  5. Microphone DC bias

    calibrateMicBias() averages 2000 samples at 200 µs intervals, so roughly 0.4 seconds, to find the amplifier's quiescent point. Keep the room quiet during boot. Expect about 2048 counts, which is 1.65 V.

  6. Sensors

    SHT3x at 0x44 with its internal heater explicitly disabled, since the heater adds self-heating error to the very reading you want. BH1750 in CONTINUOUS_HIGH_RES_MODE. Either failing is logged and survivable; the node runs with whatever answered.

  7. Network, last

    Station mode, disconnect, and the Wi-Fi state machine set to SCAN. mqttInit() derives the node id and builds the topic strings. configTime() points at pool.ntp.org. Nothing blocks; the loop takes it from here.

  8. Boot chirp and CSV header

    Two beeps at 1500 Hz, which doubles as a buzzer self-test, the threshold summary, then the CSV column header so a capture started at boot is parseable.

Self-test

Preflight.h exists because the failure modes on this board are quiet ones. A floating microphone pin does not read zero, it reads noise that looks like sound. A display with no logic supply lights its backlight. Each check resolves to one of four states.

PASS WARN FAIL SKIP

Microphone bias categories

The bias reading is used as the cheapest voltmeter available on that rail. Where it lands says what is wrong without any test equipment.

CountsCategoryVerdictWhat it means
1800 to 2150MIC_OKPASSCentred near VCC/2. Wired correctly and powered from 3.3 V.
1400 to 1700MIC_PHANTOMFAILThe pin is being weakly pulled rather than driven. Usually a missing ground or a half-seated jumper.
below 1400MIC_LOWFAILSupply is too low or the output is loaded down.
below 100MIC_DEADFAILNothing is driving the pin at all.
anything elseMIC_ODDWARNOutside every known-good window. Worth a look before trusting the dB figure.

The checks also interact. If the microphone check fails and the I²C scan finds nothing, the summary reports a likely supply or ground fault common to both, rather than two unrelated faults, because that is nearly always what it is.

The loop

loop() runs at two rates from a single pass. Three services run on every iteration, thousands of times a second. The sampling block runs once every two seconds and returns early the rest of the time. 

void loop() {
  serviceAlarm();                    // beeper state, non-blocking
  handleWifi();                      // one state transition at most
  mqttService();                     // reconnect or pump the socket

  if (millis() - lastRead < READ_INTERVAL_MS) return;
  lastRead = millis();

  // ... read, evaluate, display, publish ...
}

That early return is the whole design. The buzzer pattern needs servicing every 150 ms to sound right, and MQTT needs its socket pumped to stay connected, so neither can sit behind a two second sensor cycle. Equally, the sensors have no reason to run faster.

Order inside the sampling block

  1. Read temperature and humidity, tracking a failure counter.
  2. Read illuminance, which returns -1 on failure rather than throwing.
  3. Read sound over a 100 ms window.
  4. Evaluate alarms and publish the alert state if it changed.
  5. Render the serial panel, then the TFT panel.
  6. Emit the CSV line.
  7. Publish telemetry, which is a no-op when the broker link is down.

Alarms are evaluated before anything touches the network, and the buzzer and display come before publishing. If MQTT is slow, the room still gets told.

Wi-Fi state machine

Four states, one transition per loop iteration, no blocking calls. A failure anywhere lands in WAIT_RETRY, which waits five seconds and starts over.

MQTT is strictly downstream. mqttService() returns immediately unless the state is CONNECTED, and reconnection attempts are rate limited to one every five seconds so a dead broker does not turn into a tight retry loop.

Sound measurement

This is a relative level, not a sound level meter

The MAX4466 is an electret capsule and an amplifier with a manual gain trimpot. Everything past its output voltage is assumption. Report the figure as a relative acoustic level calibrated at two points, never as a certified dB(A) reading.

The number is built in four steps.

  1. Find the DC operating point at boot. calibrateMicBias() averages 2000 quiet samples into micBias, around 2048 counts.
  2. Sample for 100 ms in ten sub-windows. Each 10 ms sub-window computes the RMS of (sample - micBias), which is the AC component with the DC offset removed.
  3. Convert each sub-window to decibels and keep both the mean across sub-windows (soundAvgDb) and the largest (soundMaxDb).
  4. Reject rail glitches. The ESP32 ADC occasionally returns exactly 0 or 4095, and does so more often with Wi-Fi active. Those samples are dropped before the RMS, because a single spike wrecks the whole window. 
dB = 20 × log10(Vrms / MIC_REF_V) + MIC_DB_OFFSET + MIC_CAL_DB

MIC_REF_V     = 0.00631   // 6.31 mV/Pa, the bare electret
MIC_DB_OFFSET = 94.0      // 1 Pa reference
MIC_CAL_DB    = -77.0     // this unit, set 2026-08-28

Averaging and peak are both kept because they answer different questions. A steady classroom hum and one slammed door can produce the same average; only the peak distinguishes them, so the peak is what the alarm uses and both are published.

Calibration

MIC_CAL_DB is not optional. MIC_REF_V and MIC_DB_OFFSET describe a bare electret capsule, but the module's trimpot multiplies the signal by somewhere between 25 and 125 times, adding a fixed offset of roughly 28 to 42 dB. Left at zero, a 40 dB room reads about 115 dB and the alarm never stops.

The current value came from measuring a room at about 39 dB while the panel showed about 116 dB, giving 39 minus 116.

Setting it on a new unit

  1. Zero it and flash

    Set MIC_CAL_DB = 0, flash, and let the room go quiet.

  2. Read the panel

    Note the steady average figure from the status panel, not the peak.

  3. Measure the room for real

    Use an SPL meter or a phone app. A quiet room is around 35 to 40 dB.

  4. Subtract and reflash

    MIC_CAL_DB = real_dB - panel_dB. Flash again and confirm the panel now agrees at the quiet end.

  5. Verify at the loud end

    Play a steady tone or run a noisy appliance and compare panel against meter. If the error is a constant offset everywhere, adjust MIC_CAL_DB. If it is correct when quiet but wrong when loud, the amplifier is clipping: turn the trimpot down about half a turn counter-clockwise and redo the quiet calibration.

Reading SOUND_DEBUG

With SOUND_DEBUG true, every read prints its raw statistics. Check these before trusting any decibel value.

Alarms

Each quantity has a band, a hysteresis margin and a beep pattern. The margin is what stops a reading sitting exactly on a limit from chattering the buzzer on and off every two seconds.

AlarmRaises atClears atPatternTone
Temperature <18.0 or >30.0 °C back inside by 0.5 3 beeps2200 Hz
Light <300 or >800 lx back inside by 25 2 beeps1200 Hz
Sound peak >70 dB back inside by 3 4 beeps1700 Hz
Boot chirp once, at startup n/a 2 beeps1500 Hz

Beeps are 150 ms on, 150 ms off, driven entirely from serviceAlarm() against millis(). A new alarm arriving mid-pattern is ignored rather than queued, so patterns never interleave into something unreadable.

The sound alarm is gated on calibration

evaluateAlarms() skips the sound branch entirely while MIC_CAL_DB is zero. An uncalibrated reading is tens of decibels high and would alarm continuously. The value is still measured, still displayed and still published, with sound_calibrated: false marking it as untrustworthy.

TFT dashboard

A 480×320 landscape dashboard, redrawn once per sample. Four reading cards, each with an icon, a value, a unit and a bar showing where the reading sits inside its band, plus a header carrying the alarm banner, the Wi-Fi indicator and a clock.

When any alarm is active the affected card's background switches from the surface colour to the alert colour, so the state is legible from across a room where the numbers are not.
